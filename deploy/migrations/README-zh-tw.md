# 違規證據識別資料遷移

請先透過部署時的資料庫遷移流程執行下列指令稿，再啟動新版應用程式。應用程式啟動時不會套用遷移。

遷移清單也包含 `20261101_01_model_publications.sql`，用來建立模型發布 CLI 需要的持久化發布紀錄。執行這項遷移不會變更現有模型目錄項目或啟動模型發布。

1. 套用 `20261030_01_evidence_identity.sql`。這一步新增可為空值的 ID、約束與索引，並保留舊版名稱外鍵。一般索引建立期間會阻擋寫入，大型資料表請安排在維護時段執行。取得鎖定有等候時間上限。
2. 若仍有舊版程式寫入，請在步驟 1 後套用 `20261031_01_legacy_evidence_site_dual_write.sql`。觸發程序依目前工地名稱精確比對，補上缺漏的 `site_id`，遇到未知名稱會拒絕寫入。既有明確 ID 與歷史快照均予保留。函式會綁定實際的資料表結構描述，包括證據與通知位於不同結構描述的安裝方式。
3. 部署會同時寫入 `site_id` 與歷史名稱、可接受證據事件 ID 的應用程式版本。沒有 ID 的舊資料列和新資料列皆可讀取。名稱用於顯示當時的快照，權限判斷使用目前的工地 ID。媒體檔名與公開網址沿用既有格式。
4. 重複執行 `20261030_02_backfill_evidence_sites.sql` 直到 `remaining` 為零。請查明無法比對的工地名稱，勿推測無對應工地的證據歸屬。
5. 驗證上傳、查詢與工地清理後，套用 `20261030_03_contract_evidence_sites.sql`。之後可以重新命名工地並保留證據快照。開放重新命名前須停用舊版寫入程式。已安裝過渡期觸發程序時，即使舊版程式仍使用目前工地名稱，也可完成結構驗證。逐步切換期間 ID 可為空值，請等舊版寫入程式永久停用後再以後續遷移強制 NOT NULL。

步驟 5 之前可重新部署舊版應用程式回復，新增的可空值欄位和索引可保留。步驟 5 之後，只有在所有快照名稱仍對應原工地時，才能還原舊版名稱外鍵。請勿自動回復已重新命名的快照。

串流工作程序會將尚未送出的事件留在 `VIOLATION_OUTBOX_DIRECTORY`（預設為 `outputs/event-outbox`）。Docker Compose 在該處掛載持久化具名資料卷，並為應用程式使用者初始化私有權限。原生工作程序請將該目錄保存在本機持久儲存空間。每台攝影機的預設上限為 100 筆事件、256 MiB。待送佇列已滿時會回報錯誤，通知計時不會往前推進。工作程序重新啟動後會繼續處理待送事件。FCM 重試沿用已上傳的證據 ID，上傳重試也使用同一個 UUID，因此 HTTP 回應狀態不明時不會多建立一筆證據。

證據儲存以 UUID 去除重複項目，通知中心紀錄則以收件者和違規 ID 判定是否重複。推播採至少一次傳遞，若供應商已接受推播但回應逾時，裝置仍可能收到重複通知。

## 遷移執行工具

使用與目標服務相同的受保護環境或設定檔。必須提供資料庫名稱，工具會與實際連線的伺服器核對。預設僅產生計畫，使用 `--check` 時若仍有待執行遷移，會回傳失敗狀態。

```bash
python -m deploy.migrations.run --expected-database DATABASE --config /private/service.json
python -m deploy.migrations.run --expected-database DATABASE --config /private/service.json --apply --backup /private/new-backup-directory --backup-verifier-config /private/isolated-verifier.json
python -m deploy.migrations.run --expected-database DATABASE --config /private/service.json --check
```

設定檔可包含 `environment` 物件，也可直接包含各環境欄位。未提供 `--config` 時，工具從程序環境讀取 `DATABASE_URL`，不會自行載入版本庫的 `.env`。可重複指定 `--schema` 來設定明確的搜尋路徑。需要備份時，PostgreSQL 用戶端工具必須支援伺服器版本。整個資料庫存入同一個私有備份檔。匯出的 PostgreSQL 快照確保備份與各表筆數紀錄採用同一份基準。遷移鎖定涵蓋規劃、備份、驗證及 DDL。

`--backup-verifier-config` 內含獨立驗證伺服器的 PostgreSQL `DATABASE_URL`，使用的角色須有建立資料庫的權限。驗證會建立隨機命名的 `chd_restore_...` 資料庫，還原備份，檢查所有應用程式資料表的筆數與索引有效性，並在 `finally` 區塊刪除剛建立的資料庫。既有資料庫不會被覆寫或刪除。驗證失敗時保留備份以供診斷，並在執行遷移 DDL 前停止。成功時會留下私有的 SHA256 紀錄，其中包含 `restore_verified: true`。

`manifest.json` 定義上線順序，並在回填前為舊版寫入程式建立過渡機制。工具會核對已完成階段的原始 SHA256 及完成條件，並以資料庫諮詢鎖防止同時執行。每批回填會各自提交。中斷或達到批次上限時，重新執行指令便可繼續。遇到未知工地名稱、無進展、校驗值變動或結構不符時，工具會停止，不會推測資料或將該階段標為完成。

## 通知一致性

`20261101_02_notification_delivery.sql` 新增 `sites.recipient_revision`、訂閱／身分／範圍觸發程序，以及各次裝置註冊的傳送回條。部署通知服務前請套用完整清單。新安裝的初始化程序已包含這些物件。應用程式啟動時不會執行 DDL。

查詢收件者會比較資料庫和快取的版本，Redis 租約在五分鐘後到期。偏好、帳號狀態、角色、群組或工地指派變更時，會在同一筆資料庫交易更新版本。並行重建快取時，舊版本無法覆蓋新版本。只有已啟用、明確同意接收通知且目前有工地存取權的使用者能成為收件者。

FCM 確認成功的傳送紀錄以持久化違規 ID、使用者、權杖雜湊與註冊修訂版本保存七天。重試事件會略過已成功的傳送，但新註冊的裝置可以再次收到該事件。沒有持久化違規 ID 的事件沿用短時間的語意去重機制，不共用持久化回條。供應商接受請求後，若回應在成功回條提交前遺失，仍採至少一次傳遞。

通知回條的到期清理在通知應用程式的生命週期內執行，已從通知派送流程移出。每次清理都使用到期索引、`SKIP LOCKED`、有上限的批次大小與時間預算。`NOTIFICATION_RECEIPTS_INTERVAL_SECONDS` 預設為 60，同一個前綴下另有 `BATCH_SIZE`（500）、`MAX_BATCHES`（4）和 `BUDGET_SECONDS`（2）。此維護機制沿用現有回條資料表及索引，無須額外的 PostgreSQL 遷移。

`20261102_01_model_versions.sql` 新增不可變的模型版本證據中繼資料。部署新版違規服務前請套用完整清單。它會從目前的模型目錄和發布紀錄中的可信定義回填，可重複執行，同一模型識別碼與版本若有衝突的雜湊或類別則會拒絕。往後目錄新增、更新、回復或刪除時均會在同一交易保存中繼資料。已發布版本的雜湊或類別定義無法覆寫，請發布新版本來變更。

上傳證據時會檢查目前模型的租戶、角色、工地、啟用狀態及串流能力，然後查詢所提交版本的歷史類別，不會下載或載入權重。歷史資料不包含任何授權。模型目錄和發布紀錄皆無資料的版本無法自動重建，會回傳 `MODEL_VERSION_UNKNOWN`。這些版本只能從可信的中繼資料還原。先前因 HTTP 409 而封存的事件，在遷移後仍可用待送佇列 CLI 明確放回佇列。

### 帳號與證據復原（20261102_02）

啟動新版管理和證據 API 之前，請透過遷移工具套用清單。`20261102_02_account_evidence_lifecycle.sql` 新增 `users.deletion_pending`、`violations.event_fingerprint` 和持久化的 `account_operations`、`evidence_write_operations` 作業紀錄。現有使用者沿用原本狀態。現有證據保留其影像，僅在確認重試內容相符後才補上指紋。新安裝透過 `scripts/init.postgres.sql` 取得相同結構。

刪除程序先提交本機停權狀態與刪除意圖。遠端刪除及本機清理皆可重複執行，管理 API 重新啟動後會重試未完成作業。HTTP 503 `account_deletion_pending` 表示帳號仍停權且刪除作業已排入佇列。可安全地重試已獲授權的相同使用者 ID 刪除請求。請保持 API 運作直到待辦事項完成。刪除本機使用者後仍會保留作業紀錄，重複請求可依其保存的範圍檢查授權。請勿手動重新啟用待刪除帳號。

新 Keycloak 使用者初始為停用狀態。建立帳號時會記錄不含憑證的作業 ID，在重設密碼前記錄回傳的 subject，並在提交本機帳號關聯後才啟用。若遺失遠端建立回應，狀態為 `uncertain`。自動復原不會從使用者名稱推測 subject 或刪除現有帳號。使用下列指令檢查。

```sh
python -m scripts.account_operations list
python -m scripts.account_operations retry OPERATION_ID
```

若建立狀態不確定，操作人員須核對 Keycloak 建立紀錄與使用者屬性 `visionnaire_operation_id`，再用 `retry OPERATION_ID --subject VERIFIED_SUBJECT` 明確指定 subject。此操作可能刪除尚未完成本機關聯的遠端帳號。若 subject 寫入作業紀錄失敗，應用程式日誌也會記錄作業 ID 與回傳的 subject。作業紀錄與日誌皆不含密碼。啟用失敗時會保留已關聯的身分並再次嘗試啟用，不會刪除已成功提交的本機帳號。

證據上傳會先暫存影像並執行 fsync，之後才將檔案放到正式位置，再於同一筆資料庫交易中提交證據並移除寫入意圖。提交前取消會清理該作業擁有的檔案。若提交回應遺失，會保留影像直到復原流程確認紀錄是否存在。證據 API 每 30 秒檢查超過一分鐘的寫入意圖，並以 PostgreSQL 諮詢鎖略過仍在工作的寫入程序。所有執行個體必須共用同一個證據儲存根目錄。重複使用事件 ID 時，正規化後的中繼資料與影像位元組必須相同。不同內容會回傳 HTTP 409 `event_id_conflict`。舊版影像位元組若已遺失則無法驗證，也會回傳衝突，不會逕行採用新內容。

### 帳號狀態版本與證據重試（20261103_01）

啟動新版管理和證據 API 前，使用現有工具套用 `20261103_01_account_state_evidence_recovery.sql`。這項遷移為 `users.state_revision` 增加樂觀並行控制、在帳號作業中記錄已同步版本，並替證據復原新增嘗試次數、錯誤與下次嘗試時間欄位。現有證據寫入意圖維持待處理，可繼續復原。既有遷移檔和校驗值不變。新安裝的初始化程序包含這項遷移的資料結構。

所有管理工作程序請一併部署。舊版程序無法辨識新的狀態、個人資料及重新命名作業。變更帳號會先鎖定並重新讀取目前使用者，再進行驗證。本機資料只提交一次，之後在相同使用者資料列鎖定與協調下，依最新已提交的狀態核對 Keycloak。HTTP 503 `account_reconciliation_required` 可能表示本機已提交但遠端同步尚待處理。請重試或用 `scripts.account_operations` 檢查。這些作業不儲存密碼。本機提交回應遺失時會讀取已提交的資料列來判定結果，回復時不會用過時的遠端快照覆蓋較新的帳號狀態。若退回舊版應用程式，請保留現有作業資料表，直到待辦作業完成。

證據復原使用 `EVIDENCE_RECOVERY_` 前綴的設定，包括 `INTERVAL_SECONDS`（30）、`MIN_AGE_SECONDS`（60）、`BATCH_SIZE`（128）、`BUDGET_SECONDS`（2）、`RETRY_SECONDS`（5）與 `MAX_RETRY_SECONDS`（300）。遇到已鎖定的寫入程序會延後且不計入失敗次數，失敗作業採指數退避。依下次嘗試時間選取作業，避免持續失敗的舊檔阻塞後續作業。取消時會等進行中的檔案同步或提交完成才釋放控制權。

帳號與證據作業共用兩個獨立的作業紀錄和控制權連線池，依來源池建立，以保留連線引數、自訂連線建立函式與事件監聽器。連線池依來源引擎的生命週期重用，應用程式關閉時一併關閉。請求持有交易時，背景作業不會占用請求連線池。請在資料庫連線額度中計入每個程序額外的兩個有限大小連線池。

### OpenWebUI 同步進度與作業保存期限（20261103_02）

部署新的管理工作程序前請先套用 `20261103_02_sync_progress_retention.sql`。它新增 `sync_parts`、`completed_at`、待處理項目的部分索引、已完成作業索引及 `account_deletion_receipts`。先前已完成的作業以升級時間為起算點，保有完整保存期間。已完成的刪除作業會回填回條，重複執行 SQL 不會延長既有回條的期限。新安裝包含相同資料結構，既有遷移校驗值不變。

OpenWebUI 同步使用持久化的帳號作業流程。本機變更只提交一次，再分別以可重複執行的步驟同步狀態、個人資料及應用程式角色，逐項記錄進度。本機提交回應遺失時會讀取已提交的資料確認結果。重試略過已完成步驟，帳號有新版本時會重設進度，以免舊值覆寫新值。角色變更僅限受管理的 OpenWebUI 角色子集，角色無變動時只執行讀取。作業紀錄絕不儲存密碼，無法自動重送密碼變更。若重設密碼的結果不確定，仍須由操作人員明確重試。

`ACCOUNT_OPERATIONS_COMPLETED_DAYS` 預設為 30，`ACCOUNT_OPERATIONS_CLEANUP_BATCH_SIZE` 預設為 128。已完成作業分批清理，保留待處理及狀態不明的作業。新刪除作業的 `ACCOUNT_OPERATIONS_DELETION_RECEIPT_DAYS` 預設為 365。詳細作業紀錄清除後，仍可依回條保留的原始授權範圍重試相同使用者 ID 的刪除請求。回條到期後，請求會回傳 HTTP 404。
這項遷移讓既有已完成刪除作業的回條保有 365 天。使用 `python -m scripts.account_operations list` 檢查待辦進度，以 `retry OPERATION_ID` 繼續執行。

所有管理、BFF 與通知執行個體請一起升級。舊版 BFF 寫入程式不強制檢查更新權杖的版本，舊版通知處理程式也仍會無條件刪除快取。沒有修訂版本的 BFF 工作階段會視為版本零，首次更新成功後遞增。PostgreSQL 不會寫入明文權杖。沒有註冊版本的舊 FCM 快取會標記為無效以重新建立，而非直接刪除。


帳號維護已將保存期限與同步分開處理。`AccountLifecycle` 協調器負責作業控制權與交易提交，`AccountSynchronizer` 負責有型別的同步計畫與逐項驗證進度，`AccountRetention` 負責完成回條與有上限的清理。執行遠端操作前會先拒絕無效的持久化進度。

在 `ACCOUNT_OPERATIONS_` 前綴中，`SYNC_INTERVAL_SECONDS` 預設為 5、`SYNC_BATCH_SIZE` 為 16、`SYNC_CONCURRENCY` 為 2、`SYNC_BUDGET_SECONDS` 為 30。獨立的 `CLEANUP_INTERVAL_SECONDS` 預設為 60、`CLEANUP_BUDGET_SECONDS` 為 2。清理逾時不會讓待辦作業被略過。同步會隔離個別作業的失敗，並重新排程逾時作業。關閉時會取消兩項維護工作，等交易清理完成再釋放連線池。這些排程變更無須新增 SQL 遷移。

### 註冊審核狀態的長度（20261120_01）

透過遷移工具套用 `20261120_01_signup_status_length.sql`，讓欄位容納既有的 `pending_admin_approval` 狀態。遷移在同一筆交易中將 `users.status` 擴大為 `varchar(32)`，並重建對應的通知失效觸發程序。既有狀態值及其檢查約束仍有效。新安裝直接使用較寬的欄位。
